### **HuaBook & Huawei Log Parser: Від Бінарного Хаосу до AI-Діагностики**

## 🖼️ Слайд 2: Проблема — Закритий бінарний "археологічний пиріг"

### **Чому логи Huawei важко аналізувати?**

1. **Закон Конвея в дії (15+ років еволюції)**:
   * Немає єдиного формату: це нашарування рішень десятка різних команд розробників.
   * Контейнер `.emap` об'єднує абсолютно різнородні дані: сирі C-структури, бінарні таблиці, TLV (Key-Value) та навіть звичайний текст під виглядом `.emap`.
2. **Дворівневе залізо (ARM + DSP)**:
   * **DSP ("Серце")**: Сигнальний мікроконтролер RTOS. Дампить мікросекундні C-структури (`dsp_wave_data`, `dsp_log`).
   * **ARM ("Мозок")**: Системний контролер (LiteOS/Linux). Пише логи EMAP (`alarmg_history`, `his_inv_rd`, `perfmg_data`).
3. **Обмеженість стандартного Modbus**:
   * Стандартні функції Modbus (FC 03/04) обмежені **252 байтами** і передають лише поточні значення, а не масиви логів.

## 🖼️ Слайд 3: Рішення — Huawei Log Parser та Modbus FC 0x41

### **Як працює вивантаження та парсинг логів?**

* **Протокол Huawei FC 0x41**:
  * Спеціальна власницька функція Modbus для почанкової передачі бінарних файлів з пам'яті інвертора.
  * **Sub-function 0x05**: Старт сесії та отримання каталогу `AD.bin` (Alarm/Access Data).
  * **Sub-function 0x06**: Почанкване читання даних блоками по **240 байт** з перевіркою CRC та номерами кадрів.
  * **Sub-function 0x07**: Завершення сесії.
* **Huawei Log Parser**:
  * Приймає здамплені дамп-архіви `.emap` / `.bin`.
  * Автоматично декодує заголовки (V100, V200, V300, V600), зміщення та таблиці.
  * Видає структуровані звіти в Excel/CSV для швидкої аналітики.

## 🖼️ Слайд 4: Структура логів та циклічний буфер (FIFO)

### **Ключові файли логів та їх призначення**

| Файл | Група | Наповнення та крок запису |
| --- | --- | --- |
| `his_inv_rd.emap` | Продуктивність | Напруга/струм по MPPT, Rin, температура (крок 5 хв) |
| `alarmg_history.emap` | Аварії | Журнал тривог із точним часом початку/завершення та кодом |
| `dsp_wave_data.emap` | Осцилограми | Форма хвилі (U, I) за мілісекунди до спрацювання захисту |
| `sun_inpt_rec.emap` | Здоров'я заліза | Вольт-амперні характеристики (IV-криві), мотогодини вентиляторів |
| `capacitor_data` | Здоров'я заліза | Показники ємності та ESR електролітичних конденсаторів |
| `usrmg_usrlog_2.emap` | Сервіс та аудит | Журнал авторизацій та дій користувачів/інженерів |

> 🔄 **FIFO Буфер**: Логи зберігаються у кільцевому буфері Flash-пам'яті (30–90 днів). Для збереження доказів аварії вивантаження має здійснюватися оперативно.

## 🖼️ Слайд 5: Практична цінність для O&M (Обслуговування СЕС)

### **Перетворення бінарних даних на фінансову вигоду**

1. **Профілактичне обслуговування (CBM)**:
   * Заміна вентиляторів при досягненні **30,000 мотогодин** (захист від виходу з ладу IGBT-модулів).
   * Моніторинг висихання конденсаторів DC-шини за пів року до їх пошкодження.
2. **Пошук "втраченої" генерації**:
   * Пошук підгораючих MC4-конекторів (скачки напруги на стрінгах у `his_inv_rd`).
   * Виявлення "лінивих" та затінених панелей.
3. **Юридичний захист**:
   * Фіксація систематичних перенапруг мережі (Код `2034` / `301`) для претензій до Обленерго.
   * Розмежування причин поломки: внутрішній брак чи зовнішній удар блискавки (`dsp_wave_data`).

## 🖼️ Слайд 6: MPPT та IV Curve Diagnostics

### **Інтелектуальний рентген сонячних панелей**

* **Принцип Smart IV Scanning**:
  * Інвертор плавно змінює напругу від `Isc` до `Voc` (100–512 точок за 10–60 секунд).
* **Діагностичні сигнатури аномалій**:
  * 📉 **Сходинки на кривій**: Часткове затінення (дерева, димарі, сусідній ряд).
  * 📉 **Прогин у центрі**: Ефект PID-деградації (Potential-Induced Degradation).
  * 📉 **Нахил плато**: Поганий опір контакту або пошкодження кабелю ($R_s$).
  * 📉 **Паралельне зниження кривої**: Забруднення поверхні (пил, пташиний послід).

## 🖼️ Слайд 7: Майбутнє O&M — Інтеграція з AI (LLM / CBM)

### **Від витягування даних до автоматизованих рішень**

```
┌────────────────────────┐      ┌─────────────────────────┐      ┌──────────────────────────┐
│  Бінарні логи (.emap)  │ ───► │   Huawei Log Parser     │ ───► │  Структурований JSON/CSV │
└────────────────────────┘      └─────────────────────────┘      └──────────────────────────┘
                                                                               │
                                                                               ▼
┌────────────────────────┐      ┌─────────────────────────┐      ┌──────────────────────────┐
│ Автоматичний регламент │ ◄─── │  AI-Аналітик (LLM / ML) │ ◄─── │  Аналіз першопричин (RCA)│
│    робіт та ремонтів   │      │ (Співставлення даних)   │      │  та деградації стрінгів  │
└────────────────────────┘      └─────────────────────────┘      └──────────────────────────┘
```

* **Root Cause Analysis**: AI співставляє тривоги `alarmg_history` із напругами `his_inv_rd` та осцилограмами `dsp_wave_data`.
* **Автоматичний генератор звітів**: Формування готового O&M-звіту та чек-листа закупівалей запчастин до виникнення аварії.
